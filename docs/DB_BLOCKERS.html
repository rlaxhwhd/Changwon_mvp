갈래 A — 데이터가 존재하지 않는다

쿼리를 아무리 잘 짜도 빈 테이블은 빈 테이블이다

A1

수강 · 강의 · 성적 데이터 적재

최우선 · 구현 블로커
현 상태
V_SUGANG(15컬럼) · V_LECT_INF(20컬럼)이 테이블도 DB링크도 살아 있는데 행이 0건이다.
왜 개발 불가
조인 쿼리가 이미 다 작성돼 있다. Ca.getGoalCour_List(ca.xml:334) · Ca.getLecList(ca.xml:2345) · Common.getLecList(common.xml:1325)가 두 테이블을 YEAR+SMT+GRAD_DIV+CURI_NUM 4컬럼 복합키로 조인한다. 코드가 없어서 안 되는 게 아니라 데이터가 안 들어와서 안 된다. 적재만 켜지면 그날 바로 동작한다.
요청
적재 활성화. 학사 원본 뷰 이름을 알고 있으므로 지정해서 요청 가능하다 — 수강전체(VIEW_SUGANG_ALL) · 수업개설(VIEW_SUUP_GAESUL). GRAD_DIV(과정구분) · GRADE · GPA · CDT_NUM(학점) 포함이 필요하다.
막히는 것
로드맵 3축 중 ‘수강 교과목 · 학과’ 축이 통째로 비어 있다. 직무 적합도 · 추천과목도 같은 데이터를 쓴다. 스킬트리 화면은 지금 학사DB 미러를 목업으로 채워 만들고 있다 — 데이터가 오면 로더만 갈아끼우게 설계했지만, 안 오면 목업인 채로 납품된다.
A2

학과 통합 · 분리 이력

확인된 공백
현 상태
이관 · 중복 · 학위과정은 STATUS_DEPT_CODE로 잡힌다. 통합 · 분리만 어느 컬럼에도 없다.
왜 개발 불가
STATUS_DEPT_CODE는 동일성 키지 이력 키가 아니다. 신소재공학부가 501→505로 이관될 때는 단대가 7에서 5로 바뀌었는데도 U04070300012가 그대로 따라갔다(폐지 다음 날 개설, 날짜로 입증). 그런데 505에서 재료금속공학과(506) · 첨단소재융합공학과(507)로 나뉘는 관계는 — 계열키가 040703과 040704로 갈라지고, SUUP_DEPT_CODE는 셋 다 자기 자신이고, 505에는 폐지일조차 없다. 존재하지 않는 관계는 어떤 쿼리로도 못 만든다.
요청
이력을 관리하는 테이블 · 컬럼이 있는지, DB링크로 열람 가능한지. 관리하지 않는다면 실무에서 무엇을 기준으로 판단하는지 — “없습니다”도 확정 답변이면 우리가 이력 테이블을 신설해 떠안는다.
막히는 것
개편 전 학과 학생이 개편 후 교수에게 상담신청을 못 한다. “작년 신소재공학부 상담 실적”을 개편 후에 답할 수 없다. 대학은 학과 개편이 상시라 이건 일회성 버그가 아니다.
A3

미부여 학적학과코드 채움

운영 직결
현 상태
MCODE.C_DEPT 595행 중 415행만 충전(70%). 하필 신설 학과가 비어 있다 — 162 전기공학과 · 519 스마트기계전자과 · 520 소방전기과.
왜 개발 불가
코드 부여는 학사DB 소관이다. 우리는 빈 값을 채울 수 없고, 추정으로 채우면 틀렸을 때 학생이 엉뚱한 교수에게 배정된다.

부여 기준도 일관되지 않다. 같은 날 개설된 같은 개편 건인데 506은 정식코드(U04070400017)를 받았고 507은 임시코드(T00000012296)에 머물러 있다. T 접두는 604 AI전기공학과에서도 나온다. 미부여 집계 시 NULL만 세면 이 건들을 놓친다.
요청
활성 학과 우선 채움 — 162 · 519 · 520 · 507 · 604. 폐과 코드 소급 부여 계획도 함께(졸업생 이력 조회에 필요).
막히는 것
자동 확장이 415개 학과까지만 적용된다. 나머지는 지금처럼 사람이 매번 매칭한다.
갈래 B — 데이터는 있는데 정의를 모른다

값은 읽히지만 무슨 뜻인지는 만든 쪽만 안다

이 갈래는 추측으로 개발하면 당장은 돌아간다. 그게 위험한 이유다 — 가설이 틀렸다는 건 몇 달 뒤 학생이 잘못 매칭됐을 때 알게 된다.

B1

학적학과코드 체계 정의서 · 계열키 관통 확약

가설 검증
우리 가설
12자리가 구분 1 + 계열 6 + 일련 5로 나뉘고, 가운데 계열키가 학부와 대학원을 관통한다. 예: 학부 전기공학과 U040501… ↔ 대학원 전기공학과 G040501…
근거
전기(040501) · 전자(040502) · 신소재(040703) · 재료(040704) 네 계열 모두에서 학부(U)와 대학원(G)이 같은 키를 공유하는 것을 실측했다. 다만 설계된 것인지 우연인지 알 수 없다.
요청
자리수 공식 정의 · 접두 U/G/T의 의미 · 계열키가 두 과정을 관통하도록 설계된 것인지 확약.

표현 주의 — DEPT_CODE가 U04050100006인 행은 없다. 상위 행을 가리키는 포인터가 아니라 같은 값끼리 묶이는 동일성 키다. “상위코드 맞나요”가 아니라 “학적 기준으로 동일 학과를 식별하는 키가 맞습니까”로 물어야 한다.
막히는 것
대학원생이 교수 상담신청할 때 교수가 안 나오는 문제. 관통이 확약되면 개발로 끝나고, 부정되면 학부↔대학원 매핑표 요청으로 되돌아간다. — 이 문서에서 답에 따라 가장 크게 갈리는 항목이다.
B2

UNIV_CODE 전체 코드값 정의서

현 상태
동기화가 00~10·91만 처리한다. 519·520이 90이라 학과명이 빈 채로 적재된다.
왜 개발 불가
90이 무엇인지 모르면 필터에 넣을지 뺄지 정할 수 없다. 그냥 통과시키면 나중에 90이 “폐지 예정” 같은 값일 때 폐과가 노출된다.
요청
전체 코드값 표. 90과 미사용 구간 포함.
B3

학과 유효성 신뢰 기준 확정

현 상태
USE_FLAG · OPEN_YEAR · CLOSE_YEAR 세 값이 서로 모순된다.
실물
709·710·711 — CLOSE_YEAR가 2025-02-28인데 USE_FLAG는 1(폐과가 드롭다운에 남음).
501 신소재공학부 — 폐지됐는데 USE_FLAG 1이라 505와 같은 이름이 둘 다 뜬다. 학생이 어느 쪽을 고르냐로 결과가 갈린다.
604 AI전기공학과 — OPEN_YEAR가 2027인데 벌써 노출된다.
왜 개발 불가
날짜 필터 자체는 우리가 짤 수 있다. 세 값 중 무엇을 신뢰해야 하는지를 정하는 건 데이터 소유자만 할 수 있다. 잘못 고르면 멀쩡한 학과가 사라지거나 폐과가 계속 남는다.
요청
“활성 학과”의 공식 판정 기준 한 줄.
B4

드림캐치 노출 뷰의 정의

정황
운영자가 전산원에 “V_ 테이블에 학과를 추가해 달라”고 요청해 온 기록이 있다.
왜 개발 불가
사실이라면 신설 학과가 우리 쪽 필터가 아니라 뷰 단계에서 이미 걸러진다는 뜻이다. 우리 코드를 아무리 고쳐도 안 나온다. 뷰 정의를 못 보면 원인을 확정할 수 없다.
요청
드림캐치에 노출되는 V_* 뷰의 정의(WHERE 조건). 학과 추가가 수동 작업인지 여부.
B5

학적학과코드 사후 변경 여부

요청
부여된 STATUS_DEPT_CODE가 나중에 바뀌는 경우가 있는지, 있다면 변경 이력 조회 방법.
왜 중요
값이 바뀌면 매일 새벽 동기화가 조용히 어긋난다. 에러도 안 난다. “안 바뀝니다” 확답만 받아도 설계가 훨씬 단순해진다 — 변경 감지 레이어를 안 만들어도 된다.
갈래 C — 마스터 등록 권한이 학교에 있다

우리가 할 수 있는 건 하드코딩뿐이다

C1

교수 겸직자의 소속 등록

하드코딩 제거
증상
산학협력단 소속 직원이지만 교수를 겸하는 인원이 학생 상담에서 매핑되지 않는다.
원인
동기화 로직이 사용자 유형이 ‘직원’이면 소속을 학과가 아니라 부서코드로 덮어쓴다. 그래서 겸직 교수의 학과 권한이 매일 새벽 사라진다.
현재 대응
사번 13225 한 명을 배치에 못 박아 되돌리고 있다. 사람이 늘 때마다 코드를 고쳐야 한다.
왜 개발 불가
학사DB에 겸직이 등록돼야 근본 해결이다. 등록만 되면 하드코딩은 그날 없어진다 — V_ADD_JOB_PART는 이미 매일 동기화되고(17행, 최근 갱신 2026-07-28) 화면 쿼리도 이미 이 테이블을 참조한다. 받을 준비가 다 돼 있고 데이터만 없다.
요청
겸직 등록이 가능한지. 불가하다면 이런 인원을 학사DB에서 식별할 다른 기준이 있는지. 사번 13225 외 동일 사례 일괄 포함.
C2

신설 학과 코드 개강 전 부여 확약

요청
신설 학과에 STATUS_DEPT_CODE가 언제 부여되는지와 개강 전 부여를 확약받을 수 있는지. 임시코드(T 접두)의 정식 전환 시점도 함께.
왜 중요
개강 시점에 안 채워지면 그 학기는 또 수동 대응이다. 이게 매년 반복돼 온 유지보수의 정체다. 확약은 코드로 못 만든다.
갈래 D — 승인 · 정책

기술이 아니라 결재가 필요한 것

D1

대학원 포함 조직 트리 사용 승인

요구사항 확정분
내용
신규 시스템은 대학원을 포함한 조직 트리를 정본으로 쓴다. 현행이 쓰는 대학원 누락본을 쓰지 않는다.
왜 승인 사항
데이터는 이미 읽힌다. 막고 있는 건 전부 우리 쪽 하드코딩이라 개발로 풀린다. 다만 “대학원생을 정식 대상으로 삼는다”는 건 정책 변경이라 전산원·학사 양쪽 합의가 있어야 한다. 대학원생 비교과 신청과 교수 상담신청은 이미 요구사항으로 확정돼 있다.
딸린 것
과정별 동명 학과가 다수 존재하므로 학과명이 아니라 (단대코드, 학과코드) 쌍으로 식별한다는 전제 확인.
D2

통합로그인 프로토콜 · 외부 인원 인증 경로

보안 결재
요청
SSO 연동 규격(LOGIN_ID / INTG_UID 대응)과 연동 절차.
같이 물을 것
외부 인원이 SSO 밖에서 자체 비밀번호로 접속하는 구조가 정식 승인된 것인지. 현행은 외부 위촉 상담사(COM_CON_INF.CONPWD)와 기업 담당자·멘토(TB_CARR_USER_LOGIN)에 이미 이 패턴을 쓰고 있다. 신규 시스템이 그대로 계승할지, 아니면 다른 경로를 마련할지는 우리가 정할 수 있는 사안이 아니다.
D3

야간 동기화 배치의 현재 가동 주체

확인된 모순
학사동기화 배치가 web.xml:20에서 주석 처리돼 미기동인데, 데이터는 최근까지 갱신되고 있다(조직 트리 최종 2026-07-28). 어떤 경로로든 돌고는 있는데 그게 무엇인지 모른다.
왜 개발 불가
소스에 없는 스케줄러는 소스를 아무리 읽어도 안 나온다. 이관 시점에 “최신 데이터”가 무엇인지 보장할 수 없고, 신규 시스템이 같은 주기를 재현해야 하는지도 정할 수 없다.
요청
현재 학사→드림캐치 적재를 수행하는 주체와 주기. 별도 스케줄러 · 외부 잡 여부.
D4

학사 유래 개인정보의 파기 주체

개인정보 정비 연계
배경
드림캐치가 보유한 인원은 113,823명이고 전량이 학사DB 미러다. 별도로 백업 사본 70개 테이블 · 215만 행이 쌓여 있고, 그중 개인정보 컬럼을 가진 것이 10개 · 44.4만 행이다 (사용자 마스터 스냅샷이 2020-06부터 4벌).
왜 개발 불가
미러는 지워도 다음 동기화에 다시 들어온다. 우리 쪽 삭제는 의미가 없다. 백업 사본은 지울 수 있지만 원본 소스 조각이 불완전해 무엇이 참조 중인지 확정되지 않았다 — 지금 지우면 되돌릴 수 없다.
요청
학사 유래 개인정보의 보존기간과 파기 주체(학사DB 쪽인지 드림캐치 쪽인지). 신규 시스템에서 미러 범위를 줄일 수 있는지 — 현재 43컬럼 전량을 받는데 실제로 쓰는 건 일부다. 보존기간 · 마스킹 · 상담기록 별도 보관 요건은 정보보호 담당과 함께 확인.
전산원 소관 아님

가져가면 안 되는 것

요청 목록이 길어지면 우선순위가 무너지고, 우리 부채를 학교 탓으로 돌리는 것처럼 읽힌다. 아래는 전부 우리가 해결한다.

증상진짜 원인주체
대학원 학과가 조교추가 · 교수배정 화면에 아예 없음 우리 동기화 필터가 학부·석사만 통과시킨다 개발
같은 학과가 두 번 떠서 배정을 두 번 함 우리 쿼리 — 단대만 다른 중복 등재를 안 묶는다 개발
하위 전공이 없는 학과가 목록에서 사라짐 OUTER JOIN이 WHERE 절에 무력화됐다 개발
대학원생이 대상 목록에서 빠짐 신분코드 '1101' 리터럴이 229곳에 박혀 있다 개발
학과 트리가 화면마다 다르게 보임 트리가 두 벌이고 227곳이 제각각 조회한다 개발
진단 문항 · 판정식 미확정 — 사용자 제공 대기 담당자
대학원 수료생을 상담 · 비교과 대상에 넣을지 정책 결정 담당자
PK 없는 122개 / 275개 테이블의 중복 판정 규칙 “무엇이 같으면 같은 행인가” — DB가 답을 주지 않는다 운영 담당자
맨 아래 한 건만 성격이 다르다. PK 없는 122개 테이블은 개발로도 쿼리로도 못 푸는데 전산원 소관도 아니다. 신규 설계는 전 테이블에 PK가 있어 지금 데이터를 그대로 부으면 적재가 실패한다. 상대가 운영 담당자라 이 미팅 건은 아니지만, 이관 착수 전에 반드시 답이 있어야 한다.
미팅 전 자체 확인

물어보기 전에 우리가 먼저 확인할 것

전산원 항목처럼 보이지만 우리 DB 계정으로 확인 가능한 것들이다. 미팅에 들고 갔다가 “그건 그쪽에서 보실 수 있는데요”를 듣지 않도록 먼저 돌린다.

확인할 것방법왜 먼저
비교과 참가자격 판정 함수 FN_GET_PRM_TRGT_YN() 본문 USER_SOURCE 조회
서비스 스키마 소속이면 바로 읽힌다		 대학원생 비교과 신청의 최종 관문. 소스 XML에는 없지만 DB에는 있을 가능성이 높다
조직 트리 두 벌의 242행 차이가 정확히 무엇인가 준비된 점검 SQL F-3 우리 문서가 “대학원이 빠진다”고 적었는데 실측과 어긋난다. 확정 전엔 이 숫자를 외부에 쓰지 않는다
학과 배정 190건의 코드가 학사 체계와 일치하는가 준비된 점검 SQL H-2 안 맞으면 A3 요청 범위가 커진다. 미팅 전에 알아야 요청 규모를 말할 수 있다
