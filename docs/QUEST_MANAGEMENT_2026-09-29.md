# 퀘스트 풀과 대상별 편성

## 이번 대화에서 확정한 범위

- 기간은 일일·월간·학기를 유지한다. 일일은 출석과 TOEIC 영단어 두 개로 고정한다.
- 시스템관리자가 활동형 퀘스트의 제목·설명·활동·목표 횟수·XP를 등록한다.
- 월간·학기는 풀에서 선택해 기간별로 편성한다. 전체 학생 또는 학년·C-CORE 유형별 대상을 지정한다.
- 전체 학생을 선택하면 유형·학년 조건은 비운다. 같은 기간에 대상이 겹치는 편성은 서버가 거부한다.
- TOEIC 이수 기준의 초기값은 60%이며 관리자가 정답 개수를 변경한다. 최대 문제 수도 1~20개에서 정한다.

## 화면과 API

- `/admin/quests/manage`: 퀘스트 풀, 일일 고정 항목 안내, 월간 편성, 학기 편성.
- `/admin/quests/missions`: ‘선택한 문제 → 개수 지정’에서 최대 문제 수/이수 정답 수를 저장한다. 이수 기준은 게시할 실제 문제 수를 초과할 수 없다.
- `/v2/main`, `/v2/growth/quest`: 동일 출석 API/DB 사용. 화면 체험용 출석/달성률을 실제 기록으로 교체했다.
- `/v2/growth/mission`: 풀이 시작 시점의 이수 기준을 표시하고 채점 결과에 이수 여부를 저장한다.
- `/system/quests/options`, `/definitions`, `/assignments`: 시스템관리자만 조회/변경. 일반 상담사·학생은 403.
- `POST /quests/sync`: 인증 학생 본인의 실제 활동을 읽고 완료·XP를 같은 트랜잭션으로 반영한다. 요청 본문에 학생·진행량·XP를 받지 않는다.

월간·학기 완료는 메인/퀘스트 보드 접근 시 자동 평가한다. 별도 주기 작업이나 외부 활동 서비스의 실시간 콜백을 추가하지 않았다. 현재 기간의 게시된 편성만 평가하므로, 종료된 기간을 나중에 방문했을 때의 소급 지급은 구현하지 않았다. 대상은 조회 시점의 현재 학년/확정 진단유형을 사용한다. 이미 지급한 보상은 활동 취소·정정으로 자동 환수하지 않는다.

## 활동의 판정 근거

| 활동 | 인정하는 서버 기록 / 기간 기준 |
|---|---|
| 출석 | `quest_attendance.attended_on`, 날짜당 1회 |
| 비교과 수료 | 현재 `program_apply.outcome_code=COMPLETED`이고 OUTCOME 이벤트의 `after_value.outcomeStatus=COMPLETED`가 존재, 최초 수료 처리 일시 |
| 상담 완료 | `counsel_request.status_code=DONE`이고 `completed_at`이 존재, 완료 일시 |
| 자격증 | `student_cert.verified=true`, 취득일 `acquired_dt` |
| AI 자기소개서 | `ai_run.kind_code=RESUME_REVIEW`이며 `ai_score` 결과가 존재, 실행 일시 |
| 채용 지원 | 실제 LIVE 지원, 현재 CANCELED 제외, 공고별 `applied_at` |

날짜 경계는 한국 시간이다. 월간은 선택한 달, 학기는 코드관리 `QUEST_SEMESTER`에 설정한 날짜를 사용한다. 과거 상담에 완료 일시가 없거나 비교과 수료 이벤트가 없으면 날짜를 추정하지 않는다. AI 서비스의 새로운 실행 기능이나 자격증 검증 기능 자체를 이번 작업에서 만들지는 않았다.

## 저장·동시성

- 마이그레이션 108: 풀·편성·편성 항목·학생 완료 테이블, 미션/풀이 이수 기준 열. 109: 메뉴/권한과 일일 개수 2 적용, 기존 진행 중 TOEIC 풀이에 60% 초기 기준. 기존 제출 기록의 보상을 소급하지 않는다.
- 관계형 풀/편성 항목/FK를 사용한다. 편성 항목에 당시 제목·조건·XP·풀 버전을 저장한다.
- 풀 변경이 기존 편성을 즉시 바꾸지 않는다. 미래 편성을 다시 저장하면 최신 풀 값을 반영한다.
- 게시 후 시작한 편성과 완료 이력이 있는 편성은 조건을 유지한다. 게시 여부 변경은 허용한다. 아직 게시하지 않은 편성은 현재 기간이라도 편집할 수 있다.
- 편성 저장은 공통 advisory lock으로 직렬화해 동시에 겹치는 대상을 등록할 수 없게 했다. 평가 중에는 공유 잠금을 사용한다.
- 완료는 `(학생, 편성, 퀘스트)` PK, 원장에는 안정된 source key. 기존 학생별 잠금/XP 상한을 재사용한다. TOEIC은 한국 날짜당 한 번 지급한다.
- 한 기간의 같은 활동은 한 번 집계하고, 실제 배정된 활동 종류만 조회한다. 목록은 서버 페이지당 20개, 편성은 최대 30개 항목이다.

## 검증 및 적용

- 새 격리 DB에서 001~109 migration/seed 적용, 이후 퀘스트·미션·TOEIC 관련 테스트 33개 통과. 권한/입력/낙관적 버전, 겹치는 대상 및 동시 저장, 기간 경계, 미검증·미완료 기록 제외, 중복 지급, 이수 기준 스냅샷을 포함한다.
- 타입 검사/프런트 빌드/변경 TS 파일 ESLint 통과. 기존 Vite `__dirname` 및 500KB 번들 경고는 남아 있다.
- Chrome 내장 MCP: 풀 등록, 1학년·진로탐색형 월간 편성 예약 저장, TOEIC 최대 20/이수 15 저장 후 API 재조회, 메인 출석 후 보드의 완료 상태 공유, 학기 미등록 안내 확인. 검증 화면 콘솔 오류 없음.
- StrictMode의 초기 취소 요청 외 퀘스트 조회 반복 루프는 없었다. 기존 공통 bootstrap은 여러 도메인을 선조회하며 이번 변경에서 재구성하지 않았다.
- 로컬 단일 측정: 옵션 20ms/1,157B, 풀 16ms/339B, 편성 43ms/622B, 학생 동기화 42ms/1,525B. 네트워크 포함 값이며 성능 보장 수치가 아니다.
- 격리 DB에서 읽기 전용 EXPLAIN ANALYZE: 대상 조회 0.235ms, 활동별 집계 0.018~0.040ms. 출석 PK, 상담 student, 자격증 PK, AI student/score, 지원 student, 비교과 student/event 인덱스 사용. 소규모 fixture 데이터 기준이다.
- 관리자 공통 화면은 기존 1280px 최소폭의 데스크톱 전용 구성을 유지한다.
- 로컬 `dreamcatch` DB에 108/109 적용, 개발 API 18100 재시작. Docker 배포 이미지는 재빌드하지 않았다.
- 검증용 풀·2091년 편성·2091년 TOEIC 미션·당일 fixture 출석을 조건 한정해 제거했다. 감사 이력은 보존했다.
- 기존 `backend/scripts/rebuild-test-db.sh`의 별도 작업 변경은 건드리지 않았다.

## 복구

### 2026-09-30 코드관리 일정 선택 추가

- 코드관리의 `QUEST_SEMESTER` 그룹에서 월간/학기 구분과 DB에 등록된 편성을 selectbox로 선택한다. 이름 검색 및 20건 페이지 이동을 제공한다. 일일은 선택 대상에서 제외한다.
- 월간은 운영 월, 학기는 활성 기본 학기 일정을 선택한다. 학기 원본 등록은 ‘기본 학기 일정 관리’에서 계속 제공한다.
- `GET /system/quests/schedules`, `PUT /system/quests/assignments/{id}/schedule`: 시스템관리자 권한, 버전 검사, 동일 편성 잠금·대상 중복 검사, 변경 사유 감사 기록을 적용한다. 일정만 수정하며 퀘스트 내용·XP 스냅샷과 대상은 유지한다. 추가 마이그레이션은 없다.
- 퀘스트 테스트 20개, TypeScript 및 변경 화면 ESLint 통과. Chrome MCP에서 월간/학기 선택과 저장 HTTP 200, 월간 2093-02-01~28 재조회, 빈 목록 안내를 확인했다. 콘솔 오류·경고 없음. 소규모 로컬 목록 조회는 네트워크 포함 18ms였다.
- 최초 로그인 500은 DB 연결 종료 로그가 있었고 재연결 후 정상 확인했다. StrictMode 초기 취소 요청 외 반복 조회 없음. 화면 전환 중 불필요한 조기 마운트를 막고 조회 취소를 연결했다.
- 임시 퀘스트·편성은 제거했다. `QA2093_SCHEDULE` 검증용 학기 코드는 append-only 변경 이력 보존을 위해 비활성 처리했다.

새 퀘스트 편성을 비공개로 전환하고 동기화/출제 신규 쓰기를 중단한 뒤 이전 앱으로 되돌린다. 기존 미션의 새 개수 범위(1~20)는 이전 API의 10/20 제약과 다르므로 배포 롤백 전에 설정 호환성을 확인한다. 지급 원장/완료/풀이 기록을 삭제하지 않는다. 적용한 migration은 수정하지 않고 추가 migration으로 복구한다.
