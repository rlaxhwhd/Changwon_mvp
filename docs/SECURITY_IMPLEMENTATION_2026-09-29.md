# SEC-01·SEC-02 및 파일 업로드 보안 적용 기록

2026-09-29. 사용자 요청에 따라 개발 중 보안을 적용했다. 개발용 **학번 / `!` 로그인과 교직원 개발 신원 선택을 유지**하며, 운영 SSO/최종 권한 정책은 이번 변경 범위에 포함하지 않았다. 기존 미커밋 작업은 보존했다.

## 적용 내용

### SEC-01: 개발 서버 비밀 파일 차단

- `vite.config.ts`: Vite fs deny에 secrets가 있는 deploy 전체, backend, 환경 파일, 비밀 확장자, scratch/log, 내부 문서·도구·그래프 디렉터리를 추가했다. 기본적인 환경/키 파일 차단도 유지했다.
- Vite 처리·SPA fallback 이전에 URL을 디코딩해 비공개 경로를 거부한다. 인코딩된 구분자, 대소문자 변형, raw/import, Windows ADS, `@fs` 변형을 회귀 검사했다.
- Vite 8.0.3 → 8.3.1, lockfile 갱신. 프록시는 브라우저가 보낸 X-DC-Token을 제거하고 서버 파일에서 읽은 토큰으로 교체한다. 토큰 교체 후 오래된 값을 계속 사용하지 않도록 요청 시 읽는다.
- 로컬 API 토큰, `dc_app`, 로컬 PostgreSQL 관리자 비밀번호를 교체했다. `backend/.env`는 DB 비밀번호 값 대신 비밀 파일 경로를 사용하도록 갱신했다. 두 DB 계정 모두 새 비밀번호 접속 성공/이전 비밀번호 접속 거부를 확인했다. 값은 문서·콘솔에 기록하지 않았다.
- 로컬 API(18100), Vite(5173)를 재시작하고 Docker API/web을 새 코드·자격증명으로 갱신했다. 외부 Oracle 계정은 변경하지 않았다.
- 재검사: `node tools/security/check_dev_server.mjs`. 비밀 본문을 읽거나 출력하지 않고 비공개 경로 12개가 403/404, 정상 경로 4개가 200인지 검사한다.
- 반복 가능한 로컬 교체 도구: `backend/.venv/Scripts/python.exe tools/security/rotate_local_secrets.py`. localhost 15432/dreamcatch/dc_app 설정만 허용하며 DB 갱신 실패 시 파일을 복구한다. 실행 후 로컬 API와 Docker API/web 재시작이 필요하다. 완료된 교체를 확인하려고 이 도구를 다시 실행할 필요는 없다.

### SEC-02: 저장 HTML과 기존 본문의 출력 보호

- 서버 `backend/app/html_security.py`: nh3 allowlist로 비교과 요약·상세 및 HTML 채용 본문을 저장 전 정제한다. script, 활성 SVG, iframe/object, 이벤트 속성, 위험 URL 등을 제거한다. 필요한 표·목록·굵기·색·정렬 서식은 제한된 목록으로 유지한다.
- 브라우저 `shared/safeHtml.ts`: DOMPurify 공통 함수로 비교과/채용 공고의 학생·교직원 공용 화면과 RichEditor 입력을 정제한다. 기존 DB 본문도 표시·편집 시 보호된다. 기존 데이터를 일괄 덮어쓰는 마이그레이션은 하지 않았다.
- Summernote 초기값·외부값·붙여넣기·드롭 경계를 정제했다. 원시 HTML 코드 보기 버튼은 제거했다. 이미지 선택/붙여넣기/드래그는 공통 이미지 검사로 연결했다. 기본 드롭의 HTML 직접 삽입은 비활성화했다.
- 고정된 저장소 SVG sprite는 사용자 입력 경로와 달라 변경하지 않았다.

### 학생·교직원 파일 업로드

| 경로 | 적용 경계 |
|---|---|
| 교직원 채용 로고/첨부 | `/job-files`, LOGO/ATTACHMENT → `files.store()` |
| 학생 채용 이력서 | `/job-files`, RESUME → `files.store()` |
| 학생 포트폴리오 첨부 | `/growth-files` → `files.store()` |
| 비교과 썸네일 | 프론트 파일 검사·캔버스 변환 + 서버 `ProgramBody.image` 검사 |
| 비교과/채용 본문 이미지 | RichEditor 이미지 검사 + 서버 HTML/data URL 검사 |

서버의 최종 판단은 `backend/app/upload_security.py`가 담당한다. 프론트 accept/파일명 검사는 안내를 빠르게 보여주는 보조 수단이다. 클라이언트를 우회한 직접 API 요청도 서버에서 거부한다.

- `.js`, `.mjs`, `.html`, `.svg`, `.php`, `.py`, `.ps1`, `.bat`, 실행 파일 등은 기존 슬롯 allowlist와 위험 확장자 검사로 차단한다. `script.js.pdf` 같은 이중 확장자도 차단한다.
- PNG/JPEG/GIF/WebP는 Pillow로 실제 형식·픽셀 크기를 검증하고 다시 인코딩한다. 메타데이터와 뒤에 붙인 바이트는 직접 이미지 업로드에서 보존하지 않는다. 애니메이션은 첫 프레임으로 정규화된다.
- PDF는 파서로 구조를 확인하고 JavaScript, 자동 실행·추가 액션, 실행/폼 전송 액션, 내장 파일, XFA 등을 거부한다. 단순 `%PDF` 머리글만 붙인 가짜 파일은 통과하지 않는다.
- DOC/XLS/PPT/HWP는 OLE 구조·형식별 스트림과 알려진 매크로/스크립트/내장 객체 영역을 검사한다.
- DOCX/XLSX/PPTX/HWPX는 ZIP 구조·필수 구성 파일·XML 및 매크로/ActiveX/내장 실행 객체를 검사한다. 검사할 수 없는 암호화 문서는 거부한다.
- 일반 ZIP에는 위에서 검사 가능한 문서·래스터 이미지·중첩 ZIP만 허용한다. **스크립트, SVG, 텍스트/소스 코드 등 허용 목록 밖 파일이 하나라도 있으면 ZIP 전체를 거부한다.** 암호화·경로 이동·심볼릭 링크·중복 이름도 거부한다. 총 1,000개 항목, 누적 비압축 40MB, 중첩 깊이 3 한도를 둔다.
- 기존 10MB 업로드 한도와 서버 생성 파일명·귀속/권한 검사를 유지한다. 다운로드를 기존 공통 `files.stream()`으로 통합하고 `nosniff`, `private, no-store`, attachment 헤더를 적용했다.

이번 검사는 **백신/악성코드 탐지 서비스가 아니다.** 정상 문서 형식 안의 모든 악성코드를 탐지한다고 보장하지 않는다. 업무용 원본 DOC/HWP/HWPX·복잡한 문서 전체 호환성 검증 및 운영 백신/CDR 도입은 별도 운영 준비 항목이다. 이미 저장된 첨부파일을 전수 재검사·삭제하지 않았다. HTML은 기존 본문에도 출력 정제를 적용했다.

## 검증 결과

### 자동 검사

- TypeScript/build 통과. Docker API/web 빌드 및 기동 성공.
- 변경 프론트/도구 파일 ESLint 오류 없음. 기존 `ProgramNotice.tsx`의 wishRevision 의존성 경고는 범위 밖으로 유지했다.
- 격리 DB `dc_regression_20260929045834_85f2d6_test`에서 **80 passed, 300 deselected**.
- 명령(backend 디렉터리): `.venv/Scripts/python.exe scripts/run_regression.py -k 'content_security or jobs or student_login or programs'`.
- 새 `test_content_security.py`: 스크립트/위장 확장자/PDF JS/중첩 ZIP/경로 이동/문서 매크로/위험 HTML/썸네일 거부와 정상 PDF·이미지·ZIP·문서 처리, 학생·교직원 API, 저장/수정/조회 검사.
- 기존 테스트의 가짜 PDF를 실제 PDF fixture로 바꿨고, 로고 바이트 동일성 대신 픽셀 동일성을 검사한다. 대형 HTML 테스트도 잘못된 base64 대신 실제 이미지로 바꿨다.
- 비공개 파일 경로 회귀: **12개 차단 + 정상 경로 4개 성공**. 초기 인코딩 경로의 SPA 200은 미들웨어 보강·Vite 재시작 후 해결됐다.
- Graft로 HTML 정제와 파일 검증의 실제 호출자를 재확인했다.

### Chrome MCP

- 내장 Chrome MCP로 `5173/login`, 학생 `/v2/main`, 교직원 `/admin/programs/new`, Docker `8080/login` 및 학생 메인을 확인했다.
- 개발용 학번/`!` 로그인: Vite 경유 200(960ms), Docker 경유 200(4,771ms); 학생 세션 `/auth/student/me` 200, 학생 메인 표시 확인. 계정 비밀번호 정책은 변경하지 않았다.
- 교직원 실제 공통 RichEditor에 무해한 실행 표식을 포함한 HTML을 붙여넣기·드롭했다. 표식 실행 false, 위험 속성/SVG 제거, 정상 굵은 글씨·색 유지 확인. 저장 버튼은 누르지 않았다.
- 실제 비교과 상세 화면의 본문 2개 영역이 정상 렌더링됐고 위험 태그/이벤트 속성은 없었다. 편집기에 `.js` 파일을 드래그하면 안내 후 거부되는 것도 확인했다.
- 교직원 첨부 `.js`/위장 PDF/위장 PNG: 전부 422(각 151/16/579ms 관측).
- 학생 이력서 `.js`/위장 PDF, 학생 포트폴리오 위장 PDF: 전부 422(52/33/125ms 관측). 거부 테스트는 새 파일을 저장하지 않았다.
- 정상 파일 생성·다운로드와 XSS 저장/수정 회귀는 격리 DB API 테스트로 검증했다. 정상 파일을 모든 실제 UI 파일 선택창에서 제출한 것은 아니다.
- Docker 학생 메인 관측 구간: API 30건, 같은 pathname 중복 없음, 콘솔 error/warn 없음. 대형 응답은 비교과 약 1.04MB, 채용 약 0.73MB로 남아 있다.

### 발견된 기존 성능 문제와 한계

- Docker 빌드와 검증이 겹치는 동안 로그인 학사 조회·교직원 상담 대시보드가 DB의 15초 statement timeout으로 500을 반환했다. 이후 재검증에서 로그인은 성공했다. 타임아웃/권한 보호 설정을 풀지 않았다.
- 로그인 SQL 계획은 학사 로컬 미러 약 114,176행을 Seq Scan했다. 빌드 후 같은 읽기 쿼리의 EXPLAIN ANALYZE는 680.853ms였다. 인덱스 부재와 호스트 부하가 관측됐지만 각각의 기여도를 완전히 분리하지 못했다. **이번 변경으로 성능 문제가 해결됐다고 보고하지 않는다.**
- Docker 메인 관측에서 여러 요청이 1~6초대였으며 목록 응답도 크다. 성능은 SEC-08에서 별도 동일 조건 비교가 필요하다. 이번에는 인덱스/스키마 변경을 하지 않았다.
- npm 설치 시 남은 전체 의존성 경고는 high 5/moderate 2/low 1. 이번 범위에서는 Vite와 새 보안 라이브러리만 변경했다. 나머지 의존성 조치는 SEC-07에 남긴다.
- 빌드의 500KB 초과 chunk 및 Vite 향후 native config 경고가 남아 있다. 전체 pytest/운영 SSO/운영 TLS/전체 파일 형식 호환성을 완료했다고 간주하지 않는다.

## Oracle 담당자 인계 — 사용자 확정

사용자 답변: **“Oracle 계정은 담당자에게 교체 요청—문서에 인계.”**

`deploy/secrets/oracle_password_local`도 개발 서버 접근 차단 범위에 포함했다. Oracle 비밀번호를 읽어 HTTP 응답과 대조하거나 외부 계정에 변경 명령을 실행하지 않았다. 실제 과거 외부 유출을 확인한 것은 아니다.

담당자 작업: 해당 외부 개발/연계 계정의 비밀번호 교체 → 로컬 비밀 파일 및 실제 연계 실행 환경 갱신 → 필요한 읽기 연계 확인. 값은 채팅·문서·로그에 남기지 않는다. 이번 세션에서 담당자에게 메시지를 발송하지는 않았다.

## 다음 작업 시 주의

- 보안 때문에 개발 로그인 `!`를 삭제하지 않는다. 운영 인증은 SEC-03으로 분리한다.
- 정상 문서가 거부되면 실제 형식/내장 객체를 확인한다. 확장자만 믿도록 되돌리거나 예외를 무조건 허용하지 않는다.
- 비밀 경로 차단·새 비밀번호를 이전 취약 상태로 되돌리지 않는다. 자격증명을 다시 교체할 경우 모든 로컬 소비자를 함께 재시작한다.
- 새 업로드 기능은 공통 서버 `files.store()` 경계를 사용한다. base64/외부 URL 경로도 별도로 검증한다.
