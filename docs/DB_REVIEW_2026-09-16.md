# DB 구조 리뷰 및 개선 — 2026-09-16

판정: 전면 재설계보다 기존 도메인 분리·원본 보존을 유지하면서 무결성·동시성·조회 경로를 보강한다.

  602개 제약, 233개 인덱스, 50개 사용자 트리거, 앱/PUBLIC grant.
- 001–082 적용 대장과 파일 체크섬 불일치 0. 업무 테이블 PK 누락 0,
  미검증 제약 0, invalid/not-ready 인덱스 0. 앱의 academic 원본 테이블 직접 grant 없음.
- 개선 후 테스트 DB: 085까지, 605개 제약, 234개 인덱스. 테이블·컬럼·트리거 수 유지.
  완전히 같은 키·연산자·정렬·조건·UNIQUE 의미를 가진 중복 인덱스 0.
- [전체 구조 명세](dbmeta/SCHEMA_INVENTORY_2026-09-16.md): 모든 테이블의 컬럼 타입,

- 재수집 도구: `backend/scripts/audit_schema.py`. REPEATABLE READ / READ ONLY / 15초 statement timeout.
  업무 행·인증정보는 출력하지 않는다. 행수는 PostgreSQL 통계 추정치이며 -1을 0으로 해석하지 않는다.
- 전수 카탈로그 검토와 도메인별 원본 코드 검토를 수행했다. 모든 업무 데이터의 의미,
  모든 API의 부하·동시성·개인정보 접근을 전수 검증했다는 뜻은 아니다.
- 시작 전부터 존재한 미션 기능 등 작업 중 변경은 보존했다. 운영 서버·학사 Oracle에는 접속하지 않았다.

## 이번 수정

### R1 — 심리검사 결과의 학생 소유권

기존 request_id/학생 개별 FK는 다른 학생의 신청과 유효한 학생 UID 조합을 허용했다.
083에서 기존 `counsel_request_student_key(id,student_uid)`를 재사용해 복합 FK를 추가했다.
신청별 결과 1건 UNIQUE는 유지하고 포함되는 옛 단일 request FK만 제거했다.
기존 소유권 불일치와 잘못된 scales/snapshot 컨테이너는 원본 읽기 조회에서 각각 0건.
척도 배열/스냅샷 객체 CHECK는 형식만 검사하고 점수·판정 기준은 추가하지 않는다.

### R2 — 심리검사 결과 저장 충돌

사용자가 2026-09-16 이 대화에서 충돌 시 거절·새로고침 방식을 선택했다.
기존 version은 증가만 했고 저장 요청이 기대 버전을 전달하지 않아 마지막 저장이 덮어썼다.
`expectedVersion` 필수(신규 0), 기존 부모 신청 잠금 뒤 결과 버전 검사로 최초 작성 경쟁도 막는다.
불일치 409, 누락 422. 버전 확인 없이 덮어쓰는 호환 경로는 두지 않는다.
화면은 편집 시작 시점 버전을 보관하고 충돌 입력을 유지한다. 최신 결과 버튼으로 교체를 명시적으로 선택한다.
저장 성공 후 응답 DTO로 캐시를 갱신해 전체 목록 GET 1회를 제거했다.
배포 시 API와 프론트를 함께 갱신해야 한다. 구 프론트 요청은 안전하게 422로 거절된다.

### R3 — 상담 건별 사건 조회 인덱스

`communications.counsel_events`는 requestId 필터와 `(created_at,id)` 순서를 사용한다.
이전 리뷰 당시 없던 읽기 경로가 생겼는데 사건 테이블에는 UUID PK만 있었다.
084: `ix_counsel_event_request_timeline(request_id,created_at,id)`.
전체 인덱스이므로 특정 사건 종류 외에도 request FK 검사에 쓸 수 있다.
전체 사용자 사건 목록·권한 조회까지 모두 이 인덱스로 최적화됐다는 의미는 아니다.

| 항목 | 이전 | 이후 |
|---|---:|---:|
| 동일 임시 테이블, 8,000 상담 키 × 30 사건, 240,000행 | 23.217ms | 0.058ms |

`benchmark_counsel_events.py`: 실제 컬럼 구조를 복제한 TEMP 테이블, PK 공통,
같은 SELECT, JIT off, ANALYZE, 준비 조회 제외 7회 실행 중앙값.
기존은 Seq Scan → Sort, 이후 인덱스를 이용한 선택적 조회. 측정은 DB 실행시간이며 네트워크/API/권한 JOIN은 제외한다.
TEMP의 local buffer와 합성 분포이므로 운영 개선 배수나 8천 사용자 동시접속 성능으로 일반화하지 않는다.
실행 계획 원본은 [합성 벤치마크 JSON](dbmeta/COUNSEL_EVENT_BENCHMARK_2026-09-16.json), 재현 스크립트는 저장소에 남겼다.

### R4 — 상담 슬롯의 NULL 조합

기존 `slot_end IS NULL OR slot_start<slot_end`는 시작/종료 중 하나가 NULL인 경우를 통과시킨다.
시작만 있으면 DTO가 종료 시각을 포맷할 때 오류가 날 수 있다.
085에서 시작/종료 쌍과 시각 존재 시 날짜를 강제했다. 원본의 위반 조합 0건.
날짜만 있는 교수/심리 직접 상담 기록, 예약 없는 신청은 계속 허용한다. 날짜·시각을 만들어 보정하지 않는다.

기존 NULL 진단 점수, 빈 학사 수강, 공식 배점 미수신은 0/합격/완료로 치환하지 않는다.
정규화 후속의 핵심은 `student.detail/roster`·`staff.profile` 중 **현재값을 판정에 쓰는 필드**를
출처·NULL 규칙이 있는 컬럼/관계로 옮기는 것이다. 원문과 과거 snapshot까지 일괄 분해하는 것은 권하지 않는다.
보존 기간·학사 키 중복 처리·공통 동의·외부 진단 갱신 규격은 기존 DB.md 미결을 유지한다.

## 적용·복구 절차

- 기존 001–082 파일은 변경하지 않는다. 배포 전 `audit_schema.py`와 백업을 실행한다.
- 083 사전조회: 부모 학생 불일치, jsonb_typeof(scales) != array, snapshot != object. 위반 시 원본 근거로 해결하고 재시도한다.
- 085 사전조회: 시작/종료 NULL 불일치, 시각은 있으나 날짜 없음. 임의 시각 생성 금지.
- 083–085는 현재 실행기의 한 트랜잭션에서 원자적으로 적용된다. lock_timeout 5초, statement_timeout 30초.
  잠금·검증 실패 시 전체 트랜잭션 rollback 후 원인을 해소한다. 운영 규모의 validation/lock 지속시간은 미측정이다.
- 큰 운영 event 표는 쓰기 차단 시간을 피하도록 동일 정의 인덱스를 별도 owner 세션에서
  `CREATE INDEX CONCURRENTLY ix_counsel_event_request_timeline ON dc.counsel_event(request_id,created_at,id)`로 선생성한다.
  `indisvalid`, `indisready`, `pg_get_indexdef`로 **이름뿐 아니라 정의가 정확한지** 확인 후 084를 적용한다.
  실패한 concurrent 인덱스는 재사용하지 않고 상태 확인 후 별도 복구한다.
- API·웹을 함께 갱신하고 동일 충돌 동작을 재확인한다. DB 인덱스 변경만으로 기존 실행 API 코드가 바뀌지는 않는다.
- 되돌릴 때 과거 파일/대장을 지우지 않고 신규 forward migration을 만든다.
  083은 옛 request 단독 FK를 먼저 복원한 뒤 새 3개 제약 해제, 084는 추가 인덱스만 DROP,
  085는 새 슬롯 CHECK만 해제한다. 정상 작동 시 제약을 제거할 이유는 없다.
  코드 rollback 시에도 결과 행·스냅샷·점수는 그대로 보존한다.
