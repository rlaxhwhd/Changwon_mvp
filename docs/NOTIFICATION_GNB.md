# GNB 알림 표시·읽음 정책

2026-09-21 사용자 요청 반영. 학생·관리자 포털의 공용 NotificationBell에 적용한다.

- 목록, 스크롤 추가 조회, 미읽음 배지 모두 현재 시각 기준 최근 23시간만 대상으로 한다. 기존에는 캐시만 23시간으로 제한하고 서버 목록은 전체 기간을 조회했다.
- 마우스 올리기는 미리보기이며 읽음 처리하지 않는다. 알림 아이콘 클릭(키보드 활성화 포함)은 패널을 열고 본인에게 수신된 알림을 일괄 읽음 처리한다. 개별 항목 클릭은 필요하지 않다.
- `POST /api/v1/notifications/read-all`은 로그인한 수신자만 대상으로, 처리 시작 시각까지의 알림을 저장한다. 아직 로딩하지 않은 항목과 과거 알림도 포함한다. 이후 새로 발생한 알림은 미읽음으로 유지한다.
- 기존 `notification_read`의 PK와 `ON CONFLICT DO NOTHING`으로 반복 요청을 안전하게 처리한다. 동일 순서로 삽입하며 다른 수신자의 알림은 수정하지 않는다.
- 캐시를 즉시 표시하되 열 때 첫 페이지를 재검증한다. 페이지 번호를 표시 행 수와 독립적으로 관리한다. 전체 읽음과 목록 조회가 동시에 진행돼도 늦게 도착한 목록 응답 때문에 읽음 표시가 돌아가지 않게 처리 시각을 보관한다.
- CSV 내보내기는 기존 전체 이력 계약을 유지한다. 표시 기간 제한으로 DB 이력을 삭제하지 않는다.

## DB 검토

새 스키마나 마이그레이션은 없다. 기존 `ix_notification_recipient(recipient_uid, occurred_at DESC, id)`가 수신자·시간 필터·정렬에 대응하며 `notification_read` PK가 읽음 조인과 중복 방지에 사용된다. 전체 읽음은 항목마다 HTTP/SQL을 호출하지 않고 INSERT SELECT 한 번으로 처리한다. postgres-patterns, Supabase Postgres 지침 및 프로젝트 DB 리뷰 기준을 적용했다.

## 검증

- 격리 DB `dc_regression_20260921005515_bf7f4c_test`에서 알림 테스트 3개 통과: 23시간 전후 경계, 오래된 since 필터, 페이지네이션, 전체 읽음 반복 호출, 다른 수신자 보호, 미래·후속 알림 미읽음 유지.
- TypeScript 포함 프로덕션 빌드 및 수정한 프론트 파일 ESLint 통과.
- Chrome MCP로 테스트 DB에 연결된 관리자 GNB 확인: 최근 알림 25개·3일 전 알림 1개를 준비했고, 배지 25→0, 처음 20개 및 스크롤 후 전체 25개 읽음 표시, 오래된 알림 제외, 재로딩 후 읽음 유지 확인.
- 최초 클릭 시 목록 GET 31ms, 전체 읽음 POST 38ms, 요약 GET 19ms, 모두 HTTP 200. 로컬 테스트 조건의 관측값이며 운영 성능 보장은 아니다. 콘솔 오류·경고 없음.
- 실사용 DB의 알림은 변경하지 않았다. 실행 중인 API에는 새 코드를 로딩하는 재시작(또는 자동 reload)이 필요하다.
