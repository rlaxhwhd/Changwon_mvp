# 비교과 신청 상태 및 설문 진입 버튼

## 동작

학생 공고 `/v2/growth/program/:id`와 내역 `/v2/mypage/programs`가
`ProgramParticipationActions`와 `shared/myPrograms.ts`의 상태·설문 판정을 공유한다.

| 본인 신청 상태 | 표시 및 동작 |
| --- | --- |
| 미신청 | 기존 신청하기/신청 마감 |
| 선발 대기 | 선발대기중 |
| 선발, 사전 설문 미제출, 운영 시작 전 | 사전 설문조사 진행 → PRE |
| 선발, 사전 설문 제출 또는 조사 미실시 | 선발완료 |
| 수료, 사후 역량 설문 미제출 | 사후 설문조사 진행 → POST |
| 수료, 만족도 미제출 | 만족도 조사 진행 → SATISFACTION |
| 수료, 실시하는 설문 모두 제출 | 이수완료 |

사후·만족도 둘 다 남으면 두 링크를 표시한다. 취소·탈락·미수료에는 설문 진행 링크를 표시하지 않는다.
기존 `survey_window` 규칙을 유지하므로 운영 시작일부터 사전 설문은 닫힌다.
신청 마감 공고라도 기존 신청자의 상태와 가능한 설문을 먼저 표시한다.
마이페이지에서는 상태와 설문 버튼을 함께 표시하고 기존 상세 모달의 제출 내역을 유지한다.

## 데이터와 갱신

- 공고는 기존 프로그램 API의 본인 신청을 공통 참여 형태로 변환한다. 진입·창 복귀 시 해당 공고 한 건을 갱신하고, 신청 저장 후 기존 스토어 발행을 구독한다.
- 마이페이지는 기존 `/programs/mine` API를 사용하며 창 복귀 시 갱신한다. 행마다 설문 API를 호출하지 않는다.
- 설문 진입은 기존 `/v2/mypage/programs/:id/survey/:phase`와 서버 판정·제출 API를 사용한다.
- 공고 및 설문 조회에 AbortSignal을 연결했다. 개발 StrictMode의 첫 요청은 취소되고 다음 요청만 완료한다. 설문 ID/단계 변경 시 폼 상태를 새로 만든다.
- DB·마이그레이션·신청·설문 제출 기록 변경 없음.

## 검증

- 변경 TypeScript 파일 ESLint 통과, `npm run build` 통과.
- Chrome MCP, `localhost:5173`: 실제 API 데이터로 선발대기중·선발완료·이수완료 표시 확인.
- 별도 브라우저 탭에서 GET 응답만 대체하여 공고 13개, 마이페이지 12개 상태 조합의 문구와 URL 검증. 실제 DB에 시험 신청/수료/응답을 저장하지 않았다.
- 공고 PRE, 내역 POST, 공고 SATISFACTION 링크 클릭 및 실제 설문 API 200 확인. 기존 사전 응답은 제출 완료, 미수료 학생의 사후·만족도는 서버가 응답 불가로 판정하는 것도 확인했다. 이번 검증에서 설문 제출은 하지 않았다.
- 좁은 화면(실측 viewport 500px)에서 사후·만족도 버튼 2개 노출, 고정 바 높이 117px/본문 하단 여유 128px 확인.
- 관측한 정상 요청: 내역 13ms/1,513B, 공고 382ms/350,026B, 사후 설문 40ms/5,234B, 만족도 50ms/3,131B. 브라우저 네트워크 시간이며 DB 시간이나 성능 개선 수치가 아니다.
- 확인한 화면 콘솔 오류·경고 없음, API HTTP 오류 없음. 개발 모드 취소 요청은 `ERR_ABORTED`로 표시된다.
- 기존 공통 부팅 조회에는 프로그램 약 1.04MB, 채용공고 약 0.73MB 응답이 남아 있다. 공고에는 이미지/HTML이 포함된다. 이번 변경은 전체 부팅 조회 구조를 변경하지 않았다.

김채원의 `prog_59b06c5de6cc`는 확인 당시 선발 상태이며 사전 설문을 이미 제출했으므로 `선발완료`가 정상 표시다.
