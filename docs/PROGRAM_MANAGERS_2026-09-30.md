# 비교과 복수 담당자·신청 알림·사전 설문 시작 시각

## 확정 규칙

- 신청 알림 수신자는 프로그램에 지정된 담당자 전원이다. 학생 담당상담사나 등록자는 프로그램 담당자에 포함될 때만 수신한다.
- 등록·수정 화면에서 직원 선택 → 담당자 추가, 선택된 담당자별 제거가 가능하다. 새 프로그램은 로그인 직원이 기본 선택된다.
- 사전 설문은 선발 후 한국시간 운영 시작 **일시** 전까지 열리며, 이수 결과 확정 후에는 닫힌다. 사후·만족도는 기존처럼 수료 후 열린다.
- 시각이 없는 기존 프로그램은 시작일 자정 기준을 유지한다. 누락된 시각을 임의로 채우지 않는다.

## 원인과 변경

`survey_window()`가 `run_start <= today()`로 판정하여 9월 30일 16:15 시작 공고도 당일 자정부터 사전 설문을 닫고 있었다. `run_start + run_start_time`을 Asia/Seoul로 비교하도록 수정했다. 설문 GET·POST와 주간 일정이 같은 함수를 사용한다. 주간 일정 조회에도 `run_start_time`을 전달한다.

`program_manager`는 `(program_id, staff_uid)` PK, `(program_id, position)` UNIQUE, 프로그램·직원 FK를 가진다. 프로그램 삭제 시 담당자 연결만 CASCADE한다. `staff_uid, program_id` 역방향 인덱스를 둔다. 기존 `program.manager`는 공고의 표시·검색 호환용 문자열이며 지정 ID 목록으로부터 서버가 만든다.

API는 `managerIds`에 기존 직원 alias를 받고 DB에는 통합 직원 ID를 저장한다. 학생 ID·미등록 ID·중복 ID는 거부한다. 목록은 담당자를 한 번에 조회하여 프로그램별 N+1을 만들지 않는다. 기존 클라이언트가 필드를 생략하면 기존 연결을 유지한다. 기존 이름의 동명이인 매칭은 추측하지 않는다.

신청 저장과 알림 INSERT는 같은 트랜잭션이다. 담당자 수정과 신청은 같은 프로그램 행 잠금으로 직렬화한다. 수신자·소스 종류·프로그램/학생 조합 UNIQUE와 기존 신청 idempotency로 중복 알림을 막는다. 기존 신청에 대한 소급 알림은 만들지 않는다. 담당자 변경은 이후 신규 신청 알림부터 적용한다. 알림의 읽음·최근 23시간 목록·페이징은 기존 공통 API를 재사용한다.

알림 클릭은 `/admin/programs/:id/applicants`로 이동한다. 브라우저 검증에서 기존 ProgramShell이 부팅 시점 캐시만 읽어 새 신청자를 놓치는 문제가 확인되어, 진입/탭 이동 시 단건 API를 새로 조회하고 공통 PROGRAM_EVENT를 구독하도록 수정했다. 로딩·실패·재시도 화면을 제공한다.

## 검증

- 새 통합 테스트 11개 + 기존 공고 연결 8개: 19개 통과.
- 기존 설문 중 현재 복제 DB와 일치하는 5개 통과. 기존의 설문 문항 총수 84개 가정 및 삭제된 jiwoo를 사용하는 2개는 제외했다.
- 주간 일정 테스트 6개 통과. 기존 날짜 고정 fixture를 새 시각 판정에 맞춰 한국시간 정오로 고정했다.
- 15:55, 16:14:59에 PRE GET 열림/POST 201, 16:15(UTC 07:15) 및 16:25에 닫힘/POST 409. 주간 일정의 closed 판정도 일치.
- 담당자 3명 수신, 등록자·다른 상담사·다른 학생 미수신, 남의 알림 읽음 404, 중복 요청 중복 알림 없음, 담당자 변경 및 구형 PUT의 목록 유지 검증.
- TypeScript 및 변경한 TSX/타입 파일 ESLint 통과.
- Chrome MCP: 복제 DB의 김태정으로 기존 `ㅌㅅㅌ` PRE가 실제 16:15 이전에 응답 가능 표시됨을 확인. 실제 응답 데이터는 제출하지 않았다.
- Chrome MCP: 관리자 편집에서 담당자 1→3명 추가·저장·재조회, 3→2명 제거·저장 확인. 썸네일 카드에도 담당자 전원이 표시되며 가로 넘침 없음.
- Chrome MCP: 복제 DB의 별도 공고 신청 모달 제출 → 신청 201 → 담당자 3명 알림 생성 확인. GNB 알림을 클릭해 신청자 관리로 이동, 캐시 1명인 상태에서 추가된 두 번째 신청자까지 2명 표시 확인.
- 측정: 검증 공고 단건 47ms(TTFB 40ms, 수신 5ms, 63,126B), 알림 목록 25ms(TTFB 20ms, 수신 2ms, 1,000B). 서버 처리 시간 헤더가 없어 TTFB를 서버/DB 시간으로 단정하지 않는다.
- 실제 DB EXPLAIN ANALYZE: 담당자 단건 묶음 조회 0.512ms, 수신자 조회 0.032ms. 작은 현재 데이터셋 측정치이며 대규모 성능 보장이 아니다.
- 확인한 최종 화면 콘솔 오류·경고 없음. 개발 StrictMode에서 첫 GET이 취소되고 다음 GET 200으로 완료되는 요청은 구분했다. 기존 전체 부팅 시 카탈로그·프로필 다건 조회 구조는 이번 변경 대상이 아니다.

## 최종 접속 확인 중 발견한 로그인 조회 지연

실제 18100/5173 접속 확인에서 학생 로그인 POST가 statement timeout으로 500이 되었다. 로그인 쿼리는 로컬 학적 미러 114,176행에 인덱스 없이 전체 검색을 수행하고 있었다. 실제 DB의 동일 파라미터 EXPLAIN ANALYZE에서 35,283.022ms, shared buffers 3,989개를 확인했다. Docker 빌드가 함께 실행된 환경이라 이 숫자를 평상시 응답 속도로 일반화하지 않는다.

113은 학생번호 해석식 `COALESCE(NULLIF(login_id::text,''),intg_uid::text)` 및 `intg_uid`에 비고유 인덱스를 추가하고 ANALYZE한다. OR 양쪽 인덱스를 BitmapOr로 결합한다. 로그인 조건·학생 종류 필터·권한·원본 데이터는 변경하지 않으며 중복 신원은 여전히 거부한다. 테이블은 로컬 미러이고 API는 쓰지 않는다. 인덱스 생성의 잠금 대기 제한은 5초다.

- 복제 DB 적용 후 동일 조회 실행 시간 0.504ms, 이후 실제 DB 적용 후 0.137ms 및 shared buffers 8개. 측정 시 시스템 부하가 같다고 보장하지 않으므로 배수 개선 주장은 하지 않는다. 전체 검색 제거는 실행 계획으로 확인했다.
- 기존 로그인 테스트는 2개 통과, 2개 실패. 이 테스트의 고정 입력 `20180001`이 가져온 학적 미러에 이미 존재하여 fixture INSERT 후 2건이 되었고, 서버는 의도대로 401을 반환했다. 실제 학생 데이터를 지우거나 중복 신원 거부를 해제하지 않았다.
- 별도 TestClient로 고유 신원 200, `/me` 200, 로그아웃 204 및 이후 `/me` 401, 중복 신원 401, 없는 신원 401을 확인했다.
- 실제 5173 김태정 로그인도 인덱스 적용 후 성공하여 학생 메인으로 이동했다.
- 113은 복제 DB 검증 후 실제 로컬 DB에 적용했다. 코드 롤백 시 인덱스를 유지하며, 제거가 필요하면 별도 후속 마이그레이션을 사용한다.

Docker 갱신 중 16:35–16:37에 PostgreSQL worker exit code 2와 자동 복구 로그가 발생하여 개발 API의 기존 DB 연결에서 500이 났다. 컨테이너 자체 OOMKilled=false/RestartCount=0였으며 worker 종료의 근본 원인은 이번 로그만으로 단정할 수 없다. DB의 recovery 완료 후 개발 API를 다시 시작해 연결 풀을 재생성했고 Docker 3개 서비스 Healthy를 재확인했다. 반복되면 PostgreSQL/호스트 진단이 별도로 필요하다. 이 일시 장애를 프로그램 코드 오류 또는 인덱스 효과로 설명하지 않는다.

기존 전체 부팅은 여전히 여러 도메인을 순차/동시 적재하고, 8080 신규 화면에서 metadata GET 2회가 관찰됐다. Docker 빌드·재기동 직후 실제 공고/설문 요청이 각각 3.6초/5.6초 걸린 구간도 있었다. 작은 검증 요청의 25–47ms 측정치를 전체 화면 로딩 보장으로 사용하지 않는다. 전역 부팅·metadata 로더의 성능 개편은 이번 담당자/설문 수정에 포함하지 않았다.
