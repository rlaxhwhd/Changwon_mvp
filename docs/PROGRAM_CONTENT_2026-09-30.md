# 비교과 공고·신청 연결 (2026-09-30)

## 확정 정책

- 공고일시 전에는 학생 공고 목록·상세·공고 첨부 다운로드에 노출하지 않는다. 교직원은 미리 확인할 수 있다.
- 접수 시작/마감은 한국 시간의 날짜와 시간을 함께 판정한다. 기존 시간 미지정 기록은 시작일 00:00~마감일 종료까지 유지한다.
- 기존 지원경로·지원동기·동의 항목을 유지하고 관리자가 설정한 추가 질문을 아래에 표시한다.
- 추가 질문은 필수 여부를 설정한다. 필수 동의 문항도 동의/미동의 응답을 받으며 미동의를 임의로 신청 거절로 해석하지 않는다.

## 변경

- 관리 탭 체크박스 → 선택 삭제 → 확인. 실패한 항목은 선택을 유지하고 항목별 원인을 안내한다.
- 이수 결과·로드맵·설문 응답·관심 등록 이력·역량 배점 참조는 삭제하지 않는다. 기존 FK 보호를 409 안내로 처리한다.
- 신규 담당자는 로그인 교직원으로 초기화한다. 담당자 입력과 미리보기의 값을 통일했다.
- 공고일시와 접수/운영 시간을 저장·재조회하고 학생/교직원 공용 공고에서 날짜·요일·시간으로 표시한다.
- 공고 첨부 업로드·제거·다운로드 및 썸네일 카드 이미지 표시를 연결했다. 공고 첨부는 20개, 파일당 기존 공통 정책 10MB를 따른다.
- 질문 종류는 단일선택/복수선택/500자 서술/동의서/첨부이며 선택지·동의문·필수 여부·최대 첨부 개수를 저장한다.
- 답변은 신청 당시 질문 정의와 함께 스냅샷으로 남는다. 이후 질문 수정은 기존 답변을 바꾸지 않는다.
- 신청자 관리의 추가정보·첨부 보기에서 답변을 확인한다. 파일 다운로드에도 본인/신청자 조회 범위를 검사한다.
- 날짜 없는 공고에서 카드 목록이 예외로 중단되던 문제를 수정하고 마감 표시를 공통 함수로 통일했다.

## 저장·권한·조회 검토

- 새 migration 110은 nullable 시간 필드와 기본값이 빈 질문 배열인 JSONB를 추가한다. 기존 데이터 시간을 추측하여 채우지 않는다.
- 질문은 공고의 작은 종속 문서라 JSONB를 사용한다. 질문 ID 중복·허용 형식·선택지·배열 크기는 API에서 검사하고 DB는 배열 타입을 확인한다.
- 수정은 기존 version 대조와 program 행 잠금, 신청은 기존 멱등키와 program 행 잠금을 유지한다.
- 첨부는 기존 file_object 소유 인덱스를 이용해 목록당 한 번에 조회한다. 프로그램별 N+1 조회를 추가하지 않았다.
- 파일 저장 이름과 검증·크기 제한·다운로드는 기존 files/upload_security 경로를 재사용한다. 다른 사람의 임시 파일을 귀속할 수 없다.
- 테스트 복제 DB에서 EXPLAIN ANALYZE: 공고 첨부 조회 0.070ms, 공개 공고 목록 ID 조회 0.106ms. 7개 파일/35개 공고의 작은 데이터 실측이며 대규모 성능 보장은 아니다.

## 검증

- 로컬 DB를 복제한 `dreamcatch_program_content_test`에서 새 통합 테스트 8건 통과.
- 비교과 운영/설문/버전 선택까지 확대 실행: 35건 통과, 기존 데이터 가정 2건 실패.
  - 설문 문항 수를 84로 고정하지만 현재 복제 DB는 85건이다.
  - 기존 설문 통계 테스트가 삭제된 jiwoo 학생을 신청시켜 404가 발생한다.
  - 테스트에 맞추기 위한 실제 학생·문항 데이터 변경은 하지 않았다.
- Chrome MCP: 김진로 신규 담당자, 실제 등록과 수정 재조회, 공고 09:35/접수 10:15~18:35/운영 15:20~17:45 표시 확인.
- Chrome MCP: 생성한 800×450 테스트 이미지로 공고 업로드 및 썸네일 표시, 학생 신청서에 필수 주관식과 선택형 노출, 실제 신청 201, 상담사 화면 답변 조회, 관리 탭 선택 삭제 확인.
- MCP 파일 선택 도구는 설정된 workspace root 제한으로 로컬 파일 경로를 받지 못했다. 브라우저 내에서 생성한 테스트 이미지 파일을 input change로 전달해 실제 업로드 API와 DB 저장을 검증했다. PDF는 별도 API 통합 테스트로 검증했다.
- 학생 신청 흐름의 콘솔 오류/경고 없음. 상세 조회 200, 신청 201, 후속 조회 200. 개발 StrictMode의 첫 상세 GET 취소 1회는 정상 취소다.
- 기존 부팅 프로그램 전체 조회는 테스트 DB에서 약 1.2MB/136ms였다. 기존 base64 이미지와 전체 프로그램 적재 구조의 영향이며 이번 변경으로 전체 목록 구조를 전환하지는 않았다.
- 실제 Docker 재기동 직후 첫 프로그램 목록 요청은 4,678ms였다. 동일 URL 재조회는 66ms(TTFB 31ms, 본문 전송 23ms), 7건/1,174,770바이트로 측정됐다. Server-Timing이 없어 TTFB를 서버 처리 시간으로 단정하지 않는다. DB 조회 실측은 위의 별도 실행 계획을 참고한다.
- TypeScript/Vite 빌드 및 변경 파일 ESLint 통과. 기존 Vite native-config 전환 안내 및 500KB admin chunk 경고는 남는다.

## 로컬 적용 및 복구

- 실제 로컬 DB 적용 전 백업: `backend/var/before-program-content-20260930.dump` (Git 제외).
- migration 110 적용. 기존 데이터 삭제/예시 프로그램 삽입은 실제 DB에 하지 않았다. 브라우저 쓰기 검증은 복제 DB에서만 수행했다.
- 로컬 Docker API·웹 재빌드/교체 완료, DB/API/web 모두 healthy. 실제 `http://localhost:8080/admin/programs/new`에서 김진로 기본 담당자·첨부 입력·추가 설정과 새 API 필드 200, health 200, 콘솔 오류/경고 없음을 확인했다.
- 격리 검증에 사용한 18103 API·5174 Vite 서버는 종료했다.
- 검증 완료 후 이번 작업에서 만든 복제 DB `dreamcatch_program_content_test`를 제거했다. 실제 `dreamcatch` DB는 유지한다.
- 새 버전을 다른 컴퓨터/서버에 적용할 때는 migration을 먼저 적용한 뒤 API와 웹 이미지를 함께 갱신한다. 회사 서버에는 이 작업에서 배포하지 않는다.
- 되돌릴 때 이전 앱을 먼저 배포하고 추가 컬럼과 파일 용도는 보존하는 것이 안전하다. 컬럼을 제거해야 한다면 신규 질문·시간·파일 메타를 별도 보관한 뒤 새 forward migration으로 제거한다. 이미 적용한 110 파일을 수정하거나 파일 allowlist를 새 파일이 남은 상태에서 축소하지 않는다.
