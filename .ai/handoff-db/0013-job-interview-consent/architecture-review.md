Graft 구조 그래프는 코드와 동기화되어 있었다. HTTP 라우트는 그래프 호출자가 없으므로 실제 프런트 경로와 테스트를 직접 확인했다. 대상 코드 파일은 승인 커밋과 diff가 없었다. 실제 서버의 164 적용 상태는 팀장 작업지시서의 근거이며 본 리뷰어가 직접 측정한 사실은 아니다.

세션과 독립적인 학생·버전별 동의는 별도 테이블이 적절하다. 세션 시작 전 동의만 저장하거나 여러 세션이 같은 동의를 사용하는 cardinality를 표현한다. 기존 세션의 동의 필드는 사건 당시 스냅샷으로 유지한다. 현재 API는 새 동의의 버전과 정확한 세 항목 `privacy/media/provision`, 모든 값 `yes`를 검사한다. 프런트와 서버의 버전은 `2026-11-16`으로 일치한다.

## 정합성·백필·불변성

- `(student_uid, consent_version)` PK가 학생·버전 중복을 차단한다. 학생 FK, NOT NULL, 버전 길이 1–40, JSON 객체 CHECK, timestamptz가 기존 164 계약과 일치한다. 별도 surrogate ID나 중복 인덱스는 필요 없다.
- `DISTINCT ON`과 `ORDER BY student_uid, consent_version, agreed_at, id`는 학생·버전별 가장 이른 행을 결정적으로 선택한다. 동일 시각도 id로 결정한다. 기존 세션 행을 변경하거나 삭제하지 않으며 당시 답변과 시각을 그대로 옮긴다.
- 164 DDL만으로는 모든 답변이 yes임을 보장하지 않는다. 이전 API는 현재와 같은 버전/키/yes 검증을 했다. 따라서 운영 백필 전 기존 세션의 실제 답변·버전을 집계 검증해야 한다. 수동 입력 등으로 불완전하거나 거부 답변이 발견되면 배포를 중지하고 처리 방침을 검토한다. 부적합 기록을 동의 완료로 간주해서는 안 된다.
- 165의 UPDATE 트리거는 예외를 발생시키고 앱에는 SELECT/INSERT만 부여한다. DELETE/TRUNCATE는 앱 권한으로 막는 구조이며 소유자·슈퍼유저의 삭제까지 막는 구조는 아니다. 앱 역할의 상속·기본 ACL·소유권을 실제 DB에서 확인한다. 광범위 DELETE/TRUNCATE 권한이 있으면 해당 환경은 승인 전제와 다르므로 수정 후 재검증한다.
- 새 세션은 저장된 동의의 version/answers/agreed_at을 복사한다. 불변 행을 읽으므로 외부 호출 전후 UPDATE 경쟁이 없다. 세션과 동의의 추가 복합 FK는 없고 스냅샷 계약은 API와 기존 세션 불변 트리거가 유지한다.

## 권한·동시성·쿼리

조회와 동의 기록은 인증된 principal의 `intg_uid`만 사용하며 학생 kind를 검사한다. 사용자 입력으로 타인의 uid를 선택할 수 없다. 시작도 `require_deep` 학생 검사와 자기 자소서 조회를 거친다. 응답에는 동의 원본이나 학생 목록을 노출하지 않고 `consented` boolean만 더한다. RLS가 아닌 기존 서버 권한 경계를 따른다.

`ON CONFLICT (student_uid,consent_version) DO NOTHING`은 동시 재동의에도 최초 커밋 기록을 유지한다. 재요청은 성공하지만 시각과 답변을 바꾸지 않는다. 면접 시작 자체는 외부 API 생성 작업이어서 이 변경이 중복 시작의 멱등성을 새로 보장하는 것은 아니다. Deep 호출 전에 동의 조회 연결을 반환하고 새 세션 쓰기 때만 다시 연결한다.

| 주요 경로 | 인덱스 및 비용 판단 |
|---|---|
| 학생·현재 버전 동의 1건 조회/충돌 확인 | 새 복합 PK로 정확 조회. 학생 FK 역조회도 선두 컬럼 사용 가능 |
| 본인 세션 최신 50개 | 기존 `ix_job_interview_session_student(student_uid, created_at DESC)` 사용 가능 |
| 기존 세션에서 최초 동의 백필 | 1회 전체 읽기·정렬. 실제 행수와 소요 시간은 복원 DB에서 확인 |

목록은 최대 50건과 동의 조회 1회로 N+1이 없다. DB 내부 SELECT *로 작은 JSON 스냅샷까지 읽지만 DTO는 필요한 필드만 응답한다. 이 변경에 응답 크기나 지연 개선 수치를 주장할 근거는 없다. 현재 규모에서 별도 JSON GIN 인덱스는 필요하지 않다.

## 마이그레이션·배포·롤백 조건

1. 승인 SQL의 checksum과 실제 배포 artifact를 고정한다. 새 테이블·함수·트리거·백필은 `migrate.py`의 단일 트랜잭션과 migration advisory lock 안에서 적용한다. SQL 자체는 재실행용 IF NOT EXISTS 방식이 아니다. 실행기는 적용 기록과 checksum으로 재실행을 건너뛰며 실패는 전체 롤백한다. 적용된 SQL을 고치거나 ledger를 임의 삭제하지 않는다.
2. 격리 테스트 DB와 서버 백업의 복원 DB에서 아래 검증을 완료한다. lock_timeout 3초, statement_timeout 30초를 넘으면 중단 원인을 조사하며 검증 없이 timeout을 해제하지 않는다.
3. **운영 적용 전 기존 인터뷰 쓰기를 중단하고 진행 중 요청을 drain한다.** 구 API는 새 consent 테이블을 쓰지 않으므로 백필 SELECT 이후 구 API가 세션을 추가하면 동의가 누락된다. 백필 시작부터 신 API 전환까지 쓰기 공백이 있어야 한다. 배포 직전 백업 및 기존 데이터 비교 기준은 이 정지 구간에 만든다.
4. DB 적용 → API·웹을 한 릴리스로 교체 → 조회 검증 후 재개한다. 신 프런트 start body는 동의 필드를 제거했고 구 프런트는 여전히 해당 필드를 보내므로 혼합 버전은 422를 낼 수 있다. 기존 열린 탭의 새로고침 필요성을 운영 절차에 포함한다.
5. 장애 시 API와 웹을 함께 이전 버전으로 복구하고 **165 테이블과 ledger 및 동의/세션 데이터는 보존**한다. SQL 주석의 DROP은 데이터 손실을 동반하므로 일반 롤백으로 실행하지 않는다. 구 API로 복구한 동안 새 세션이 쌓이면 재배포 전에 누락 동의 보강이 별도 승인된 절차로 필요하다. 이미 존재하는 불변 동의를 덮어쓰지 않는다.
6. DB_SCHEMA.md에 164/165 구조와 보존 롤백 설명을 보완한다. 업무 원칙은 DB.md의 2026-11-16 동의 1회 규칙을 따른다.
